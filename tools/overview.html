thermal-cam / overview

Raspberry Pi 5 · e-ink preview · 58mm ESC/POS printer — read of master @ ee848ed

What it is

A handheld: camera → e-ink preview → thermal-print the shot. Four GPIO buttons, no screen UI.

pi/ is the only code that runs on the device. arduino/, esp-idf/ and python/ are abandoned prototypes kept for reference — the Arduino TPrinter.cpp is genuinely useful as the reference implementation, the rest is history.

Architecture

pi/main.py is one ThermalCamera class plus three concurrent pieces:

_capture_loop
main.py:433		 Grabs frames flat-out while self.capturing. Pushes (image, timestamp) into a maxsize=1 queue, evicting the stale frame first.
_display_loop
main.py:457		 Pulls a frame, stashes it as current_image under a lock, dithers, blits to e-ink. The queue.Empty branch doubles as the save trigger.
main thread
main.py:537		 Sleeps in a 0.1 s loop. All input arrives via gpiozero callbacks (main.py:181), which run on gpiozero's own threads.
camera→queue(1)→dither→e-ink │ current_image→384 px→DC2 * chunks→paper

The queue is a frame dropper, not a buffer. The camera runs far faster than an e-ink refresh, so most frames are discarded by design. Printing doesn't touch the queue at all — _action_print (main.py:391) snapshots current_image under the lock and re-processes it independently.

Two divergent image paths from the same source frame: prepare_for_display letterboxes onto a 176×264 canvas; prepare_for_printer scales to 384 px wide with no padding. Both Floyd–Steinberg dither to 1-bit.

The printer driver

pi/lib/ext/printer.py — Ladyada's Arduino library ported to Python. print_bitmap (printer.py:330) is where every recent commit went. Three constraints stack:

1 · 9600 baud, not 19200

The upstream default corrupts every byte, and corrupted bitmap data trips the printer's default kanji mode. That's the "prints Chinese characters" failure.

2 · Chunks capped at 3 rows printer.py:363

The command buffer is ~255 bytes; a 384-px row is 48 bytes, so 5 rows is the hard ceiling. The code uses 3 to leave pacing headroom.

3 · Inter-chunk pacing printer.py:395

Counts black bits per chunk, estimates burn time from heat_time/heating_dots, sleeps 1.25×. Without it the buffer overflows mid-stream and header bytes print as text. This is the fix behind "spams kanji in middle of the image" → "good".

Config gotcha

DISPLAY_WIDTH=264, DISPLAY_HEIGHT=176 are the landscape dimensions. The panel is natively 176×264. DISPLAY_ROTATION=90 swaps them back at main.py:233, and getbuffer handles both orientations.

It is consistent and it works — it's just indirect. The constants don't mean what their names suggest, which is exactly the kind of thing that costs an hour in six months.

Suggestions

ponytail · lite — you asked me to run this past the lazy-senior filter. Three things stand out.

The RGB/RGBA branches in convert_pixel_array_to_binary are dead

prepare_for_printer always hands you a mode-'1' image, so pixels[0] is always an int and only the single-channel branch ever runs. The other two branches are ~25 lines that cannot execute — and one of them is wrong: sum(p[0:2]) / 3.0 sums two channels and divides by three. Delete both branches rather than fix them.

Most of printer.py is upstream you never call

print_markup, all four barcode methods, upsidedown, inverse, offline/online, has_paper, the output_png debug path, and the __main__ demo that references a missing example-evren.png and a Image.ANTIALIAS constant Pillow removed in v10. The device uses print_text, print_bitmap, linefeed, justify, sleep. That's five methods out of twenty-odd.

Counterpoint, and I'd take it: it's a vendored third-party driver. Vendored code you don't maintain is cheaper left whole than pruned — pruning it makes future upstream diffs unreadable for no runtime gain. Leave it. Just delete the print("hi"), which is yours, not theirs.

Don't build the menu system

GPIO 6 has been reserved across five commits and still does nothing. Either it has one job you can name in a sentence — and then it's a two-line callback, not a ui.py — or it doesn't need to exist yet. A menu framework for a four-button device with a 1.5 s screen refresh is the classic thing that eats a weekend and ships nothing.

The keeper: the burn-time pacing at printer.py:395 is real hardware calibration, derived from the datasheet's heat model and matched against the Arduino reference. It looks like a magic sleep. It isn't. Don't let anyone "simplify" it into a fixed delay — including me on a later pass.
